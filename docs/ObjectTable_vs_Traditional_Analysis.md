# ObjectTable vs 전통적 방식 (Rectangle + AnalogTag/Text) 비교 분석

## 결론 요약

| 항목 | ObjectTable (신규) | 전통적 방식 (Rectangle + Text) |
|------|-------------------|-------------------------------|
| **성능 이득** | 소~중 (규모에 따라 다름) | 기준 |
| **편의성** | 매우 높음 | 낮음 |
| **유지보수** | 쉬움 | 어려움 |

> 성능 이득은 **소규모 테이블(3x3)에서는 미미**하고, **대규모 테이블(10x10 이상)에서는 유의미**하다.
> 편의성 이득은 규모와 무관하게 **압도적**이다.

---

## 1. 오브젝트 수 비교

전통적 방식으로 테이블을 만들려면 **셀당 최소 2~3개 오브젝트**가 필요하다:

| 구성 요소 | 역할 |
|-----------|------|
| ObjectRectangle | 셀 배경 + 테두리 |
| ObjectText / ObjectAnalogString | 텍스트 또는 태그 값 표시 |
| (선택) ObjectLine | 그리드 선 보강 |

```
전통적 방식: 오브젝트 수 = (행 × 열) × 2~3
ObjectTable:  오브젝트 수 = 1
```

| 테이블 크기 | 전통적 방식 (오브젝트 수) | ObjectTable |
|------------|--------------------------|-------------|
| 3×3        | 18~27개                  | 1개         |
| 5×5        | 50~75개                  | 1개         |
| 10×10      | 200~300개                | 1개         |
| 20×20      | 800~1,200개              | 1개         |

## 2. 메모리 사용량

### ObjectExpand 기본 클래스 오버헤드 (객체당)

각 ObjectExpand 인스턴스가 상속 체인에서 갖는 필드:

| 계층 | 주요 필드 | 추정 크기 |
|------|----------|----------|
| ObjectPublic | basePoint, screenSize, moduleSize, opacity 등 | ~60-80 bytes |
| ObjectFont | LOGFONT, Font 캐시, 계산 캐시 | ~120-150 bytes |
| ObjectExpand | 위치(4개), 색상(4개), 선 스타일, 스크립트 슬롯 7개, 슬라이더 2개, 마우스존 | ~400-500 bytes |

**ObjectExpand 1개당 기본 오버헤드: ~600-700 bytes**

### 전통적 방식 10×10 테이블 메모리

```
셀 200개 (Rectangle 100 + Text 100) 기준:

오브젝트 메모리:     200 × ~700 bytes  = ~140 KB
ExpandScript 구조:   200 × ~80 bytes   = ~16 KB
GDI 브러시/펜:       200 × 2-3개       = 400-600 GDI 핸들
Font 객체:           200개 (캐시되더라도 참조 유지)
문자열 할당:         200+ strings

총 추정: ~200-300 KB + GDI 리소스 부담
```

### ObjectTable 10×10 테이블 메모리

```
ObjectExpand 1개:                      ~700 bytes
ObjectArgsTable (설정):                ~200 bytes
TableCellData 100개 × ~60 bytes:       ~6 KB
columnWidths + rowHeights (List<float>): ~200 bytes
tagBindingCache (Dictionary):           ~2 KB (태그 사용 시)

총 추정: ~10 KB
```

| 테이블 크기 | 전통적 방식 | ObjectTable | 절감률 |
|------------|------------|-------------|--------|
| 3×3        | ~15 KB     | ~3 KB       | ~80%   |
| 10×10      | ~200 KB    | ~10 KB      | ~95%   |
| 20×20      | ~800 KB    | ~30 KB      | ~96%   |

## 3. 렌더링 성능

### 전통적 방식

```
프레임당 처리:
1. ObjectPublicGroupLayer가 자식 순회
2. 각 자식에 대해 Display() 호출
   → 좌표 변환 (zoom, origin, rotation)
   → DisplayObject() 호출
   → GDI 드로잉 (FillRectangle, DrawRectangle, DrawString 각각)
3. 클리핑/가시성 체크: 오브젝트별 수행

10×10 테이블 기준:
- Display() 호출: 200~300회
- GDI DrawString: 100회
- GDI FillRectangle: 100회
- GDI DrawRectangle: 100회
- 좌표 변환: 200~300회
```

### ObjectTable

```
프레임당 처리:
1. Display() 1회 호출
2. DisplayObject() 내부에서:
   - 배경 FillRectangle: 1회
   - 셀 배경 FillRectangle: ~100회 (루프)
   - 셀 텍스트 DrawString: ~100회 (루프)
   - 그리드 선 DrawLine: ~20회 (10+10)
3. 좌표 변환: 1회

총 GDI 호출: ~220회 (비슷)
좌표 변환: 1회 (200~300회 → 1회)
가상 함수 호출: 1회 (200~300회 → 1회)
```

### 렌더링 성능 비교

| 항목 | 전통적 방식 | ObjectTable | 차이 |
|------|------------|-------------|------|
| Display() 가상 호출 | 200~300회 | 1회 | **대폭 감소** |
| 좌표 변환 | 200~300회 | 1회 | **대폭 감소** |
| GDI 드로잉 호출 | ~300회 | ~220회 | 소폭 감소 |
| 가시성 체크 | 200~300회 | 1회 | **대폭 감소** |

> **GDI 드로잉 자체는 비슷**하지만, 그 위의 오버헤드(가상 함수 디스패치, 좌표 변환, 가시성 체크)가 크게 줄어든다.

## 4. 태그 업데이트 (타이머 이벤트) 성능

### 전통적 방식

```
타이머 틱마다:
- EventTimerObject() 200~300회 호출
- 각 오브젝트가 개별적으로 태그 값 조회
- 값 변경 시 각각 InvalidateObject() 호출 → 개별 영역 Invalidate

태그 조회: 100회 (각 텍스트 오브젝트)
Invalidate: 변경된 셀 수만큼 (최악: 100회)
```

### ObjectTable

```
타이머 틱마다:
- EventTimerObject() 1회 호출
- tagBindingCache Dictionary 순회
- 변경된 셀이 있으면 InvalidateObject() 1회

태그 조회: 100회 (동일 - 태그 수는 같음)
Invalidate: 최대 1회 (전체 테이블 영역)
```

| 항목 | 전통적 방식 | ObjectTable |
|------|------------|-------------|
| EventTimerObject 호출 | 200~300회 | 1회 |
| 태그 값 조회 | 100회 | 100회 (동일) |
| InvalidateObject 호출 | 최대 100회 | 최대 1회 |

> 태그 값 조회 자체는 동일하지만, **이벤트 디스패치 오버헤드와 Invalidate 횟수**가 크게 줄어든다.

## 5. 마우스 이벤트 처리

### 전통적 방식

```
클릭 시:
- ObjectPublicGroupLayer가 자식 200~300개 순회
- 각각 WmLeftButtonDown() 호출
- 각각 좌표 히트 테스트
- 첫 번째 히트에서 중단 (평균 절반 순회)
```

### ObjectTable

```
클릭 시:
- WmLeftButtonDown() 1회 호출
- 내부에서 행/열 인덱스 계산 (O(rows + cols))
- 즉시 셀 식별
```

## 6. 편의성 비교 (가장 큰 차이)

### 전통적 방식으로 5×3 테이블 만들기

```
필요 작업:
1. Rectangle 15개 배치 (각각 위치/크기 수동 조정)
2. Text/AnalogTag 15개 배치 (각각 Rectangle 위에 정렬)
3. 각 텍스트에 태그 바인딩 설정 (15회)
4. 헤더 행 스타일 별도 설정 (색상, 볼드 등)
5. 정렬 맞추기 위해 좌표 미세 조정
6. 열 너비 변경 시 → 30개 오브젝트 전부 이동/리사이즈
7. 행 추가 시 → Rectangle + Text 새로 배치 + 기존 것들 재배치

예상 작업 시간: 15~30분
```

### ObjectTable로 5×3 테이블 만들기

```
필요 작업:
1. ObjectTable 1개 배치
2. Property 페이지에서 행/열 수 설정
3. 셀별 텍스트/태그 입력
4. 열 너비 변경 → 비율 조정 1회
5. 행 추가 → 숫자만 변경
6. Excel에서 복사 → 붙여넣기 (PasteFromExcelText)
7. HTML 테이블 → 붙여넣기 (PasteFromHtml)

예상 작업 시간: 1~3분
```

### 편의성 기능 (ObjectTable만 제공)

| 기능 | 전통적 방식 | ObjectTable |
|------|------------|-------------|
| Excel 붙여넣기 | 불가능 | `TablePasteExcel` |
| HTML 붙여넣기 | 불가능 | `TablePasteHtml` |
| 셀 병합 | 불가능 | `TableMergeCells` |
| 동적 크기 변경 | 매우 어려움 (스크립트로 수십 개 오브젝트 조작) | `TableSetSize` |
| 셀 색상 동적 변경 | 개별 오브젝트 스크립트 필요 | `TableSetCellColor` |
| 선택된 셀 하이라이트 | 직접 구현 필요 | 자동 지원 |
| 클릭된 셀 식별 | 매우 복잡 | `TableGetSelectedCell` |

## 7. 최종 평가

### 성능

```
소규모 (3×3):   성능 차이 체감 불가. GDI 호출 자체가 적어서 오버헤드 무시 가능.
중규모 (10×10): 메모리 95% 절감, 이벤트 디스패치 200배 감소. 체감 가능.
대규모 (20×20): 메모리 96% 절감, 이벤트 디스패치 800배 감소. 확실한 차이.
```

**성능 이득은 테이블 크기에 비례하여 증가한다.** 순수 GDI 드로잉은 비슷하지만,
프레임워크 오버헤드(가상 함수, 좌표 변환, 이벤트 디스패치, 메모리)에서 차이가 난다.

### 편의성

**규모와 무관하게 압도적.** 전통적 방식의 가장 큰 문제:
- 열/행 추가/삭제 시 수십 개 오브젝트 재배치 필요
- 정렬 맞추기가 수작업
- 태그 바인딩을 셀마다 개별 설정
- 런타임에서 동적 테이블 구성이 사실상 불가능

ObjectTable은 이 모든 것을 **단일 오브젝트 + 스크립트 커맨드**로 해결한다.

### 권장 사용 시나리오

| 시나리오 | 권장 |
|---------|------|
| 고정된 2~3개 값 표시 | 전통적 방식 (오버킬 방지) |
| 정형화된 데이터 테이블 (5×5+) | **ObjectTable** |
| 태그 값 모니터링 대시보드 | **ObjectTable** |
| Excel/DB 데이터 표시 | **ObjectTable** (붙여넣기 지원) |
| 동적으로 행/열 변하는 테이블 | **ObjectTable** (유일한 현실적 선택) |
