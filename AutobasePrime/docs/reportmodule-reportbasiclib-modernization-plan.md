# ReportModule / ReportBasicLib 현대화 설계안

## 목적
- 신규 보고서는 Excel이 아니라 Autobase 전용 보고서 엔진을 기본 경로로 삼는다.
- `ReportModule`은 디자이너/뷰어 제품 경험을 맡고, `ReportBasicLib`는 실행 엔진을 맡는다.
- 웹, 로컬, 스케줄러가 같은 실행 엔진을 공유하도록 구조를 정리한다.
- 향후 `XLSX`, `PDF`, `PNG`, 차트 출력까지 확장 가능한 기반을 만든다.

## 현재 판단
- `MakeRunReport`는 이미 실질적인 계산 엔진 역할을 하고 있다.
- `ReportPrint`는 현재 인쇄/미리보기 중심이지만, PNG 렌더링 재사용성이 높다.
- `FormReportChild`는 편집, 실행, 렌더링, 파일 저장, 선택 처리까지 한곳에 몰려 있다.
- 현재 제품 적합성은 좋지만, 엔진 분리도와 편집 UX는 낮다.

## 큰 방향
```text
Editor / Viewer
    ->
Report Application Layer
    ->
Report Engine Core
    ->
Data Provider / Tag Provider / DB Provider
    ->
Renderer (PNG / PDF / XLSX / CSV)
```

## 1. 엔진 개선 방향

### 1-1. 실행 엔진 분리
- `ReportRuntimeFacade`를 공용 진입점으로 유지한다.
- `MakeRunReport` 내부 로직을 점진적으로 순수 엔진 계층으로 이동한다.
- 실행 입력은 모두 명시적 요청 모델로 전달한다.
  - 템플릿 파일
  - 실행 시간
  - MinList 기간
  - 문자열 변수
  - 실행 모드

### 1-2. 정적 상태 축소
- 현재 `ReportConfig`, `ConfigVarTotal`에 흩어진 실행 상태를 요청 단위 컨텍스트로 줄인다.
- 목표는 “동시에 여러 보고서 실행”이 가능한 구조다.
- 우선순위:
  - 시간 관련 정적 값 제거
  - 문자열 변수 전역 배열 제거
  - 엔진 내부 캐시 범위 명확화

### 1-3. 계산 성능 개선
- `ArrayList`를 `List<T>`로 바꾼다.
- 셀 명령 파싱 결과를 캐시한다.
- 실행 전 템플릿 분석 단계와 실행 단계를 분리한다.
- `REPORT_STRUCT` 전체 deep copy를 줄이고, 변경이 필요한 구간만 복사하는 방향을 검토한다.
- `ChangeCommandToString` 계열의 문자열 파싱 비용을 줄인다.

### 1-4. 중간 모델 도입
- 장기적으로는 `REPORT_STRUCT`만 바로 렌더링하지 말고, “실행 결과 모델”을 따로 둔다.
- 이유:
  - PNG/PDF/XLSX 렌더러 공통화
  - 차트 추가 시 데이터 바인딩 지점 명확화
  - 편집 모델과 실행 모델의 책임 분리

## 2. 렌더링 개선 방향

### 2-1. 현재 경로
- 현재는 `REPORT_STRUCT -> ReportPrint -> Print/Bitmap`
- 이 경로는 호환성 측면에서 유지 가치가 높다.

### 2-2. 단기 목표
- PNG 렌더링은 현재처럼 웹 미리보기 기본 포맷으로 유지한다.
- 페이지 분할 결과를 그대로 내려서 긴 보고서도 다중 페이지로 표시한다.
- `PDF Renderer`를 다음 우선순위로 추가한다.
  - 웹 다운로드
  - 메일 첨부
  - 보관 파일

### 2-3. 중기 목표
- `XLSX Renderer` 추가
- 이때 `OpenXML + ClosedXML`는 템플릿 엔진이 아니라 “Autobase 보고서 결과 export” 용도로 사용한다.
  - `ClosedXML`: 시트 생성, 셀 쓰기, 스타일
  - `OpenXML SDK`: 문서 속성, 인쇄 옵션, 세부 메타데이터

### 2-4. 차트 방향
- 차트는 엔진 계산 결과 위에 추가되는 렌더링 기능으로 본다.
- 우선순위:
  1. 막대/선형 기본 차트
  2. 보고서 내 지정 영역에 차트 배치
  3. 태그/집계 결과를 차트 데이터 소스로 연결
- 차트는 편집기에서 “차트 객체”를 추가하는 방식으로 가는 것이 자연스럽다.

## 3. 에디터 UX 개선 방향

사용자 불편의 핵심은 “표 편집과 수식 작성이 직관적이지 않다”는 점이다.

### 3-1. 표 생성/이동 개선
- 표 삽입 마법사 추가
  - 행/열 수
  - 기본 셀 크기
  - 헤더 포함 여부
- 마우스로 표 이동 시 스냅 가이드 제공
- 표 선택 시 외곽 핸들 표시
- “셀 편집”과 “표 자체 편집” 모드를 시각적으로 구분

### 3-2. 셀/수식 편집 개선
- 엑셀식 수식 입력줄 같은 상단 편집 바 추가
- 현재 셀 주소 표시
- 자동완성 후보 제공
  - 함수
  - 명령어
  - 태그명
  - 시간 함수
- 셀 더블클릭 시 인라인 편집 강화
- 수식/명령 오류를 저장 전에 검증해서 알려주기

### 3-3. 속성 편집 개선
- 셀/표/헤더/푸터 공통 속성 패널 추가
- 현재는 대화상자가 많고 작업 흐름이 자주 끊긴다.
- 목표:
  - 오른쪽 Property Panel 기반 편집
  - 자주 쓰는 속성은 즉시 변경
  - 고급 설정만 별도 대화상자

### 3-4. Undo/Redo 개선
- 현재 구조는 Undo는 있으나 작업 의미가 거칠다.
- 개선 목표:
  - 표 삽입
  - 행/열 이동
  - 셀 병합/해제
  - 수식 변경
  - 스타일 변경
  를 사용자가 이해 가능한 작업 단위로 묶기

### 3-5. 대량 편집 편의
- 다중 셀 선택 후 일괄 정렬/서식 적용
- 복사/붙여넣기 범위 미리보기
- 행/열 번호 고정 표시
- 확대/축소 UX 개선
- 큰 양식 편집 시 스크롤 성능 개선

## 4. 우선순위 제안

### 1단계: 엔진 안정화
- `ReportRuntimeFacade` 중심으로 실행 경로 통일
- 정적 상태 축소
- 명령 파싱/실행 캐시 도입
- PNG/PDF/XLSX 렌더러 구조 확정

### 2단계: 에디터 사용성 개선
- 상단 수식 입력줄
- 속성 패널
- 표 삽입/이동 UX
- 저장 전 유효성 검사

### 3단계: 고급 객체
- 차트 객체
- 이미지/아이콘 객체 고도화
- 조건부 스타일

## 5. 나중에 구현할 테스트 항목
- 같은 `.rptx`에 대해 로컬 실행과 웹 실행 결과가 같은지
- 긴 보고서가 페이지 단위 PNG로 빠짐없이 생성되는지
- 문자열 변수/시간 변수 전달이 올바른지
- 대용량 표에서 편집 반응 속도가 허용 범위인지
- Undo/Redo 후 저장 결과가 깨지지 않는지

## 6. 다음 구현 추천 순서

2. 렌더링 쪽: PDF 추가
3. 에디터 쪽: 수식 입력줄 + 속성 패널
4. 에디터 쪽: 표 생성/이동 UX 개선
5. 장기: 차트 객체 추가
